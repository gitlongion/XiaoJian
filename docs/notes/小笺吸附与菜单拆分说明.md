# 小笺 0.9.11：拖动吸附对齐 + 菜单结构拆分

两件事：一件是用户能摸到的（吸附），一件是只对维护者可见的（拆分）。第二件顺手暴露了验证脚本里一个**假通过**，那个可能是这轮最值钱的发现。

---

## 一、拖动吸附

把一张卡片拖到另一张附近，8 像素以内时，边与边、中心与中心会自动贴住；贴近桌面边缘时也会贴住。

### 三条线对三条线

每张卡片在一个轴上贡献三条线：近边、中心、远边。吸附就是拿被拖卡片的这三条线，去比每个邻居（和桌面）的三条线，取**位移最小**的那一对。

所以「并排贴住」是左对右，「上下齐平」是上对上，「居中对齐」是中心对中心——同一段代码，不需要为每种情形写一条规则。

### 两轴各自判断

```csharp
int dx = OffsetFor(proposed.X, size.Width, verticals, distance);
int dy = OffsetFor(proposed.Y, size.Height, horizontals, distance);
```

纵向对齐**不会**同时把卡片横着拽走。这条如果写错（比如用一个总位移去挑最近的候选），表现是「想上下对齐，卡片却自己往左滑了一点」——很难归因。

### 吸住之后要能拖开

```csharp
_dragFree.Offset(dx, dy);              // 自由位置跟着指针
Point snapped = CardSnap.Adjust(_dragFree, ...);   // 可见位置是它被吸过去的样子
Left = snapped.X; Top = snapped.Y;
```

两个位置分开存。如果直接 `Left += dx` 再吸附，被吸住的那一下会把位移吃掉，指针再走同样的距离卡片却不动——**越拖越落后，最后跳一下**。这是「吸附」类功能最常见的错误实现。

### 其它几个决定

- **阈值 8 像素**。20 以上会让人觉得卡片不听话，3 以下基本感觉不到。自检里钉着「必须在 (0, 24]」。
- **零尺寸矩形不参与**。隐藏的卡片（`Visible = false`）边界是 (0,0,0,0)，不排除的话所有卡片都会被吸到屏幕左上角。
- **邻居列表在拖动开始时取一次**。拖动期间别的卡片不会移动，每次鼠标移动都重算没有意义。
- **桌面工作区也算目标**，所以只有一张卡片时也能贴边。

`CardSnap` 是纯算术（矩形进、点出），**能在 .NET 8 上跑真实代码**，10 项测试覆盖：远离不动、并排、齐平、两轴同时、中心对中心、桌面边缘、取最近、阈值 0、无邻居、零尺寸忽略。

## 二、菜单拆分

`BuildMenu` 原来是 **479 行**，一个方法里建完整个菜单（顶层 + 卡片设置 13 项 + 文字设置 20 项 + 打开时刷新 57 行）。

拆成四个：

| 方法 | 行数 | 职责 |
|---|---|---|
| `BuildMenu` | 115 | 只搭骨架 |
| `BuildCardSettingsMenu` | 152 | 卡片设置 |
| `BuildTextSettingsMenu` | 197 | 文字设置 |
| `RefreshMenuState` | 64 | 每次打开时刷新勾选与置灰 |

**为什么值得拆**：这个项目历史上所有「菜单项没接上处理函数」「切换语言后变成空白条目」「点了没反应」的缺陷，全部出在这个方法里。五百行里同时有构造、接线、状态刷新三种逻辑，漏掉一条太容易。

原来 `menu.Opening` 的匿名委托直接读方法里的 27 个局部变量，拆开后没法这么写。新增一个 `MenuState` 类装这 27 个引用——**不做成窗体字段**，因为菜单之外没有任何东西需要它们，而「每个菜单项一个字段」正是这个类变得难读的原因。

## 三、这一轮最值钱的发现：第 11 步是假通过

`verify_all.sh` 第 11 步「对照构建」的用途是：拿**改动前的源码**跑同一套断言，确认断言真的报得出问题。这是整套验证里最强的一环——它证明断言咬的是对的地方，而不只是「有牙」。

它原来指向 `/tmp` 里的几个旧快照。而 `/tmp` 会被清掉一半：**目录还在，`.cs` 文件没了**。于是：

```
最初改动前：卡片尺寸报出 0 条，本版 0 条
上一版交付：字号与内容库报出 0 条，本版 0 条
```

脚本读到空目录，Python 抛异常，输出里一条 `[!!]` 都没有，`grep -c` 数出 0 —— **和「全都通过」长得一模一样**。而它实际什么都没验。

改成**按需重建**：基线里没有 `.cs` 就从 `git archive HEAD` 当场重建（再打上对应版本的累计补丁）。现在这一行是真的：

```
最初改动前：卡片尺寸报出 59 条，本版 0 条
最初改动前：字号与内容库报出 287 条，本版 0 条
```

另外区分了「行为类」和「结构类」：上一版交付的对照只数行为问题。因为这一轮把菜单方法改名了，新断言去旧源码里找 `BuildCardSettingsMenu` 必然「取不到」——那不是回归，算进来只会让上一版看起来有 bug。

> **空目录比缺失更危险。** 缺失会走 `else` 分支说「跳过」；空目录会让脚本跑起来、失败、然后被当成 0 条问题。
> 凡「数问题条数」的验证，都要先确认**它真的读到东西了**。

## 四个坑

**1. 常量比较被编译器折叠。** `if (CardSnap.Distance <= 0 || CardSnap.Distance > 24) return 263;` 两个操作数都是 `const`，Roslyn 直接算出 `false`，`return` 成了不可达代码（CS0162）——**这条检查根本不存在**。必须过一遍函数局部变量。项目里早就有这个教训（`int degenerateHeight = CardState.MinCardHeight;`），我还是踩了。

**2. `$ORIG（` 会被 sh 当成变量名。** 多字节字符紧跟在 `$VAR` 后面时，`sh` 把它的字节吞进变量名，输出变成 `缺失：��这一步…`。**中文文案里的变量一律写 `${VAR}`。**

**3. `git` 的 refs 又没了。** `/tmp/XiaoJian/.git/refs/heads` 空了，`git archive HEAD` 报「branch 'main' does not have any commits yet」。objects 还在，`git fsck --lost-found` 找到唯一一个 dangling commit（就是上游那个），`git update-ref refs/heads/main <hash>` 就恢复了。

**4. 改局部变量名会让一批断言同时失效。** 把 `opacityMenu` 改成 `state.Opacity` 之后，13 条断言字符串和 3 条注入锚点全部对不上。这些是「改名必然要付的账」，逐条改完再跑反向注入确认——**注入报「找不到」时先怀疑锚点，别先怀疑代码**。
