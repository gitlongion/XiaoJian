# 卡片尺寸自由调节 —— 为什么这么写

## 一、需求

> 卡片背景最小高度和宽度固定，调整设置成任意调节大小，最小为文字区域大小

原来的卡片尺寸是**写死的**：最小 340×140、最大 700×320，就钉在三个地方——

| 位置 | 原来 |
|---|---|
| `QuoteCardForm` 构造函数 | `MinimumSize = new Size(340, 140);` `MaximumSize = new Size(700, 320);` |
| `CardState.Clamp()`（读配置文件时钳制） | 同一组数字 |
| `TransparentHitBoxForm` 构造函数 | 又写了一遍 `MaximumSize = new Size(700, 320);` |

现在改成：**下限由文字算出来**（文字区正好装下文字），**上限是桌面大小**。

## 二、为什么「文字块 + 边距」不能直接当下限

最直觉的做法是「量一下文字块，加上边距就是最小尺寸」。这条路走过三次，三次都撞墙，每次
都是模拟器（`verify_shrink_sim.py`）发现的：

### 第 1 次：下限跟着卡片一起缩

块是在**当前字号**下量的。而卡片越小、自动字号搜出来的字号越小、块也就越小、下限跟着
变小 —— 卡片顺着一条不断下移的下限一直缩，最后停在一条装不下文字的缝里。

修：参照字号改成「字号搜索的下限」7pt 这个**与卡片无关**的常量。

### 第 2 次：宽度和高度各说各话

横排文字会跟着卡片重新折行，所以「块宽」永远等于视图宽，拿它当下限等于没下限。
改成「下限宽度 = 二分找还装得下当前高度的最窄视图，下限高度 = 在**当前宽度**上量出的块高」。

结果两个轴互相矛盾：宽度是按「下限宽度」挑的，高度却是按「当前宽度」量的。把卡片拖到
300×200 时下限是 92×60，而在 92×60 这个尺寸上文字要 112px 高，根本装不下 —— 卡片被顶
回去，来回弹。

修：高度也量在**下限宽度**上。这样下限自洽了（`verify_shrink_sim.py` 的 B 组断言）。

### 第 3 次：自洽了，但下限变成一条窄条

自洽之后，「下限宽度 = 二分找还装得下当前高度的最窄视图」这条规则会把下限一路推到
**一个字一行**：12 个字的文字，最小尺寸变成 80×170 的一根竖条。文字确实不裁，但这显然
不是「文字区域大小」。

## 三、最后的写法

关键认识：**「最小的那张卡片」不是唯一的**。视图越窄、折行越多、卡片越高；把每个宽度和
它需要的高度配成对，得到的是一条曲线，曲线上的每一点都能正好装下文字。所以：

> **下限 = 这条曲线上面积最小的那一点。**

这条规则同时解决了三个问题：

| 问题 | 为什么被解决 |
|---|---|
| 下限跟着卡片跑 | 目标函数里根本没有「卡片当前尺寸」这个输入 —— 它只由文字和字体决定 |
| 两个轴互相矛盾 | 每张候选卡片都是「探针 + 那个探针下量出来的另一轴」，天然自洽 |
| 下限是一条缝 | 「一个字一行」也在同一条曲线上，而它的面积大得多，选不上 |

实现（`CardSizeLimits.MinimumFor`）：

```
探针从 10 按几何级数走到 4096（10 → 12 → 14 → … → 3799，约 48 个候选）
  横排：块 = 量(探针宽, 4096高)     卡片 = (探针 + 64, 块高 + 4 + 40)
  竖排：块 = 量(4096宽, 探针高)     卡片 = (块宽 + 4 + 64, 探针 + 40)
  候选先兜在 80×56 上，再比面积，取最小的那张
```

三个细节都是有原因的：

* **另一轴留到 4096**：只有这样量出来的块才是「不裁字」的真实足迹。横排的折行只由宽度
  决定，所以高度要放开；竖排的分列只由高度决定，所以宽度要放开。
* **几何级数而不是等步长**：等步长从 10 扫到 4096 要量四千次文字。几何步长约 48 次，
  落点离 1px 细网格的真正最优不超过 1.25 倍 —— 下限差几个像素无所谓，装得下才是硬要求。
* **退化态下限（80×56）加在候选身上，不是加在赢家身上**：加在赢家身上会把赢家抬到一个
  本来不需要抬的候选之上。2 个字的文字量正好会踩到这个坑（模拟器 C 组断言钉住了它）。

## 四、边距常量与布局的关系

`CardSizeLimits` 里那三个常量必须和 `LayoutCard()` 的实际摆法一致，否则卡片会裁掉自己的文字：

| 常量 | 值 | 对应 |
|---|---|---|
| `HorizontalMargin` | 64 | `_quoteView.SetBounds(32, 20, W - 64, H - 40)`，左右各 32 |
| `VerticalMargin` | 40 | 同上，上下各 20 |
| `TextSlack` | 4 | `QuoteView.TextMargin = 2`，视图自己左右/上下各留 2px |

`verify_size.py` 的 Z1 组直接从 `LayoutCard` 的源码里把 32/20 抠出来和常量对比。

## 五、实际能拖到多大

模拟器（度量模型：字宽 = 1.33×字号、行高 = 1.50×字号）在 7pt 下算出来的下限：

| 文字量 | 横排下限 | 竖排下限 | 说明 |
|---|---|---|---|
| 4 字 | 89×65 | 86×65 | 2×2 的方阵 |
| 12 字 | 107×75 | 123×65 | |
| 40 字 | 147×96 | 161×89 | |
| 120 字 | 184×149 | 170×160 | |
| 400 字 | 345×191 | 300×214 | |

对比原来的写死下限 340×140：小文字量能收到原来的一半以下，长文字量仍然装得下。
真机上的落点会因为 GDI 的实际字宽不同而不同，但「面积最小」这条规则不变。

**关掉自动字号时**（字号由用户自己定）：下限按**当前字号**算。字号不跟着卡片缩，
所以下限也不会跟着跑。有一个例外：卡片本来就比下限小（比如刚把字号调大），这时下限
**让位**而不是把卡片撑大 —— 撑大又会让字号跟着宽度再变，转回来又动下限。这种情况下
文字会被裁掉，和关掉自动字号之前的规矩一致。

## 六、顺带修掉的一个既有缺陷

`FitQuoteFont` 的字号搜索是 `for (float size = start; size > 7.0f; size -= 1.0f)`，
从一个小数出发，**永远踩不到 7.0f 这个下限**。于是「只有最小字号才装得下」的卡片会被留在
裁字状态。现在循环之后显式再试一次 7pt。

## 七、界面上的变化

* 「卡片大小」菜单里多了一项 **「适应文字大小（最小）」**（`Fit to text (smallest)`）：
  一步把卡片收到能装下当前文字的最小尺寸。
* 原有的「小 / 中 / 大」预设现在存的是**卡片真正的尺寸**，而不是请求的尺寸 —— 预设值可能
  被下限抬大，存请求值会导致下次打开时尺寸对不上。
* 帮助文字（中/英）补上了这两条。

## 八、验证

`sh verify_all.sh` 一次跑完七步：

| 步骤 | 覆盖 | 结果 |
|---|---|---|
| 1 | 交叉编译（net40 / AnyCPU / winexe） | 0 警告 0 错误 |
| 2 | `verify_size.py`：14 组源码级断言 + 34 处缺陷注入 | 全通过 / 全报出 |
| 3 | `verify_shutdown_path.py`：退出路径 13 组断言 | 全通过 |
| 4 | 纯逻辑测试工程（.NET 8 跑真实抽取的 `CardState` / `VerticalTextLayout` / `CardSizeLimits`） | 66 项通过 |
| 5 | `verify_shrink_sim.py`：拖动收敛模拟 | 全通过 |
| 6 | `verify_exe.py`：PE / COR20 / 元数据 / 资源 | 全通过 |
| 7 | 对照：改动前的源码 | 报出 31 条 |

模拟器的五组不变量：

* **A 下限与卡片当前尺寸无关**：7 种文字量 × 横竖排 × 6 个起始尺寸，结果必须一模一样。
  改动前的那版在这个断言下会报出 34 种不同结果。
* **B 下限处文字装得下**：横排与竖排，宽度和高度都要装得下。
* **C 下限是面积最小的那张卡片**：比「一个字一行」的窄条小，且离 1px 细网格的最优不超过 1.25 倍。
* **D 往小拖不抖动**：4 种文字量 × 横竖排 × 5 个起点，全程尺寸单调不增。
* **E 停住时 `MinimumSize` 正好等于下限**。

`verify_shrink_sim.py --old` 用被换掉的那版公式跑同一套断言，可以直接看到 A 组怎么报出来。

## 九、没有验证到的部分

macOS 上跑不了 exe。**UAC 提权、拖拽手感、GDI 的实际文字度量、真机上的落点尺寸需要在
Windows 上验证。** 具体来说：

* 度量模型里的「字宽 = 1.33×字号、行高 = 1.50×字号」是估的，真机是 GDI 的
  `TextRenderer.MeasureText`。落点尺寸会不一样，但「面积最小」这条规则不依赖系数。
* 拖拽时的流畅度：`MinimumFor` 每次约 48 次 `MeasureText`，只在换字体/换文字/换竖排和
  每次 `OnResize` 时跑。真机上如果拖拽发涩，把 `NextProbe` 的步长放大（`probe / 8` 改成
  `probe / 6`）即可，断言不依赖具体步长。
* 拖到下限时的视觉手感：文字正好贴满文字区，没有多余背景。
