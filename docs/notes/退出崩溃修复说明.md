# 退出时弹出「JIT 调试」提示 —— 原因与修复

## 一、现象

退出程序时弹出这个对话框：

```
************** JIT 调试 **************
要启用实时(JIT)调试，
该应用程序或计算机的 .config 文件(machine.config) 的
system.windows.forms 节中必须设置 jitDebugging 值。
编译应用程序时还必须启用调试。
```

这个框**不是**程序自己弹的，它是 WinForms 的默认「未处理异常」对话框。也就是说：**退出过程中，UI 线程上抛出了一个没有被捕获的异常**。

`jitDebugging` 那段话是误导——它只是在说「你没配置 JIT 调试器，所以我只能把这个框给你看」。真正要查的是异常本身。

## 二、根因

退出路径上有两个确定的缺陷，都会直接导致这个症状；还有一个同类隐患。

### 缺陷 1：在菜单自己的点击处理里把菜单销毁了

菜单项被点击时，`ContextMenuStrip` 还处在**处理自己那条鼠标消息**的过程中。而下面这些操作会当场把这个菜单销毁：

| 菜单项 | 原来的调用 | 结果 |
|---|---|---|
| 退出 | `Application.Exit()` → 关窗口 → `DisposeResources()` → `_menu.Dispose()` | 菜单在**自己的点击消息里**被释放 |
| 删除这张卡片 | `Manager.RemoveCard(this)` → `form.Close()` → `_menu.Dispose()` | 同上 |
| 新建一张卡片 | `Manager.CreateCard()` → 重建各卡片的菜单项 | 同类 |
| 透明背景 | `RecreateHandle()` | 见隐患 3 |
| 重置外观 | `ResetAppearance()` → `RecreateHandle()` | 见隐患 3 |

菜单被释放后，`ToolStrip` 还要继续收尾（关闭下拉、归还焦点、恢复激活窗口），此时它手里的对象已经不存在了 —— 异常从消息循环里漏出来，就是那个 JIT 对话框。

### 缺陷 2：在窗口自己的 `FormClosed` 事件里又关了一次

`CardManager` 原来是这样订阅的：

```csharp
form.FormClosed += delegate(object sender, FormClosedEventArgs e)
{
    QuoteCardForm closed = sender as QuoteCardForm;
    if (closed == null || !_forms.Contains(closed)) return;
    CloseForm(closed, false);          // ← 里面又调了一次 form.Close()
};
```

而 `CloseForm` 结尾是 `if (!form.IsDisposed) form.Close();`。

于是走 `Application.Exit()` 时：`Exit` → 关窗体 A → 触发 `FormClosed` → `CloseForm` → **再次 `A.Close()`** → 又进 `WmClose`。在关闭事件里重入关闭流程，是这个对话框的第二个来源。

### 隐患 3：`RecreateHandle()` 会把下拉菜单一起销毁

菜单的下拉窗口是以卡片窗口为**属主（owner）**的。Windows 的规则是：销毁属主窗口时，属主窗口的附属窗口一并销毁。所以「透明背景」和「重置外观」里的 `RecreateHandle()`，等于在菜单还开着的时候把菜单的属主窗口拆掉。

「背景颜色…」「文字颜色…」「选择字体…」「背景图片…」这些不受影响——它们先弹了模态对话框，模态对话框会先把下拉菜单关掉。

## 三、修复方式

### 1. 统一延后：`RunAfterMenu`

新增一个助手，把「会拆窗口」的工作推到当前消息处理完之后：

```csharp
private void RunAfterMenu(MethodInvoker action)
{
    if (action == null) return;
    if (IsHandleCreated && !IsDisposed && !Disposing)
    {
        try { BeginInvoke(action); return; }
        catch (InvalidOperationException) { }   // 句柄在此期间消失了
    }
    Program.PostToUi(action);                    // 线程级兜底
}
```

`Program.PostToUi` 走 `SynchronizationContext.Post`。WinForms 的同步上下文背后有一个隐藏的「封送窗口」，它在所有卡片窗口都关掉之后依然存在——这正是「最后一张卡片关闭后要求程序退出」所需要的。

改动的菜单项：**退出、新建一张卡片、删除这张卡片、卡片列表里的每一项、透明背景、重置外观**。

### 2. 退出前逐张显式关闭卡片

`CardManager.Shutdown()`：

```csharp
public void Shutdown()
{
    _shuttingDown = true;
    Program.BeginShutdown();
    for (int index = _forms.Count - 1; index >= 0; index--)
    {
        QuoteCardForm form = _forms[index];
        _forms.RemoveAt(index);
        if (!form.IsDisposed) form.Close();
    }
    _forms.Clear();
    Application.Exit();
}
```

为什么要自己关，而不是全交给 `Application.Exit()`：`Application.Exit()` 会**先逐个询问**每个窗口「可以关吗」（`Form.CheckClose()`），而**不可见的窗口不会应答**——`CheckClose()` 在 `!Visible` 时直接返回 false，`Exit` 就此中止。多卡片版本允许把卡片隐藏起来，一旦有隐藏卡片，`Application.Exit()` 就可能退不出去。自己关就绕开了这个判断。

### 3. `CloseForm` 不再二次关闭

给 `CloseForm` 加了第三个参数 `alreadyClosed`：

```csharp
private void CloseForm(QuoteCardForm form, bool removeState, bool alreadyClosed)
{
    ...
    if (!alreadyClosed && !form.IsDisposed) form.Close();
    ...
}
```

- 用户自己关窗（Alt+F4）触发 `FormClosed` → 传 `true`，只做记账，不再 `Close()`
- `删除这张卡片` → 传 `false`，正常关闭

### 4. 最后一张卡片消失后要真的退出

原来如果所有卡片都没了（例如 Alt+F4 关掉最后一张），程序会停在消息循环里：没有卡片、托盘图标也已释放，用户无从操作。现在 `CloseForm` 发现 `_forms.Count == 0` 就延后退出。

### 5. `DisposeResources` 先关菜单再释放

```csharp
if (_menu != null)
{
    if (_menu.Visible) _menu.Close();
    _menu.Dispose();
}
```

### 6. 异常兜底（防止再出现无法诊断的对话框）

`Program.InstallExceptionHandling()` 在 `Application.Run()` 之前安装：

- `Application.SetUnhandledExceptionMode(UnhandledExceptionMode.CatchException)` —— 不再走默认的 JIT 对话框
- `Application.ThreadException` —— UI 线程
- `AppDomain.CurrentDomain.UnhandledException` —— 非 UI 线程

兜底处理会：

- 把**完整堆栈**追加写入 exe 同目录的 `MyQuoteCard_error.log`（不可写则退到临时目录，UTF-8，只追加不覆盖）
- 弹一个**中文可读**的提示，告诉用户日志在哪
- **退出过程中不再弹窗**（`if (_shuttingDown && !fatal) return;`）——退出途中弹模态框会把退出本身卡住

## 四、退出时的行为

| 场景 | 现在的行为 |
|---|---|
| 菜单 → 退出 | 延后到菜单关闭后，逐张关闭卡片，再 `Application.Exit()` |
| 托盘图标右键 → 退出 | 同上（托盘菜单与卡片菜单是同一个 `_menu`） |
| 菜单 → 删除这张卡片 | 延后关闭该卡片，把托盘图标交给剩下的卡片，重新注册热键 |
| 只剩一张卡片时 | 「删除这张卡片」不可见（`CanRemoveCard` 为 false） |
| Alt+F4 关掉最后一张卡片 | 自动退出，不再留下无窗口的僵尸进程 |
| 有卡片处于隐藏状态时退出 | 照样能退出（不再依赖 `Application.Exit()` 的窗口询问） |
| 退出途中仍有异常 | 只写日志，不弹窗 |

| 补丁可应用性 | `445c501 + shutdown-fix.patch` 与 `fccd1d6 + all-changes-v3.patch` 两条路径结果**逐字节一致** |

「同一份断言在修复前报 22 条、修复后报 0 条」是这份脚本最有力的证据——它证明断言测的确实是这次改的东西，而不是一堆恒真的空话。

`verify_shutdown_path.py` 的断言要点：

- 任何菜单点击处理里直接出现的「拆窗口」调用（`Application.Exit()` / `Manager.Shutdown()` / `Manager.CreateCard(` / `Manager.RemoveCard(` / `RecreateHandle()` / `ToggleCardVisible()` / `.Close()`），必须落在 `RunAfterMenu` 的延后区块**里面**
- 点击处理里调用的方法如果会重建/销毁窗口（`RecreateHandle()`），且该方法前面没有 `ShowDialog` 挡着，这个点击处理必须走 `RunAfterMenu`
- `DisposeResources` 里 `_menu.Close()` 必须排在 `_menu.Dispose()` 之前
- `CloseForm` 必须有 `alreadyClosed` 守卫，且 `FormClosed` 订阅必须传 `true`、`RemoveCard` 必须传 `false`
- `Shutdown` 必须自己逐张关卡片
- `Program.cs` 里不许再出现裸的 `Application.Exit()`
- 异常兜底必须装在 `Application.Run()` 之前，且退出期间不弹窗

> 脚本按本项目惯例**先剥注释再断言**。本项目的注释习惯是把函数名写出来解释为什么这么写（`CloseForm` 的注释里就写着 `Application.Exit`），不剥注释会把「注释里提到过」当成「代码里调用了」。剥注释时保留字符串字面量。

## 六、局限

**UAC 提权、任务计划、以及本次的退出流程都只能在 Windows 真机上做最终确认。** 已覆盖的：编译、链接、PE 结构、资源、依赖表、字符串与引用落地、纯逻辑往返、退出路径的源码级不变量。

如果真机上退出时仍弹出提示（正常情况下应该改成弹可读提示或直接安静退出），请把 exe 同目录的 `MyQuoteCard_error.log` 发回来——里面有完整堆栈，能直接定位到具体哪一行。

## 七、怎么用

### 方式一：直接换 exe

把 `dist/MyQuoteCard.exe` 覆盖到原程序的 `dist\` 目录即可。源码只有 4 个文件，这个 exe 就是全部。

### 方式二：打补丁

在仓库根目录执行。

从**上一个修复版**继续（推荐，改动最小）：

```bash
git apply shutdown-fix.patch
```

从**上游 v0.6.1 原版**一次性打全（含隐形点击层修复、鼠标穿透、多卡片、竖排文字、退出修复）：

```bash
git apply all-changes-v3.patch
```

补丁路径以 `a/src/MyQuoteCard/...` 开头，所以在仓库根目录用 `git apply` 或 `patch -p1` 都可以。

### 方式三：直接替换源文件

`Forms.cs`、`Program.cs`、`Storage.cs` 三个文件覆盖到 `src/MyQuoteCard/`，然后按上游方式构建：

```bat
build.bat
```

### 复现验证

```bash
# 退出路径源码级断言（需要 Python 3）
python3 verify_shutdown_path.py            # 只跑断言
python3 verify_shutdown_path.py --reverse  # 再跑一遍「注入缺陷」反向验证
```
