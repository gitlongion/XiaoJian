# 小笺 0.9.10：两处缓存

这一版**没有新功能**，行为完全不变。改的是两处「做对了但做重了」的地方。

---

## 一、背景图：从「每帧重缩」到「缩一次，之后贴上去」

### 之前

```csharp
// OnPaintBackground，每次重绘都跑
e.Graphics.InterpolationMode = InterpolationMode.HighQualityBicubic;
e.Graphics.PixelOffsetMode = PixelOffsetMode.HighQuality;
e.Graphics.DrawImage(_backgroundImage, CoverRectangle(ClientRectangle, _backgroundImage.Size));
```

`_backgroundImage` 是**全尺寸位图**。一张 4000×3000 的照片贴到 460×190 的卡片上，每次重绘都要在软件里做一次双三次降采样——几十毫秒。而拖动改变卡片大小时，每一帧都在重绘。

也就是说：**配置了背景图的卡片，拖动是卡的；没配的不卡。** 这个差别用户能直接感觉到，但原因藏在绘制路径里。

### 现在

`EnsureBackgroundCache()` 按卡片的**当前尺寸**把图缩好存进一张位图，`OnPaintBackground` 只做一次 `DrawImageUnscaled`。

缓存的键有四个分量，缺一个就会画出过期的东西：

| 分量 | 为什么 |
|---|---|
| 图片引用 | 换了图要重缩 |
| 卡片尺寸 | 尺寸变了，缩好的那张就不对了 |
| 显示方式 | 换模式是**重新排布**，不只是重绘 |
| 底色 | 「适应」「居中」「平铺」三种模式会露出底色，底色变了缓存也得重做 |

两个边界：

- **超大卡片不缓存**。卡片可以拖到 8192×8192，那是 268MB 的位图——比重新缩一次还贵。超过 1600 万像素就直接画到屏幕上。
- **分配失败退回直绘**。OOM 时不能让卡片变成空白，走慢路径但结果是对的。

`DrawBackgroundPicture(Graphics, Rectangle)` 是唯一的绘制实现，缓存和直绘两条路都调它——所以「缓存里画的」和「不缓存时画的」不可能不一样。

## 二、字号：缓存按「字号」记，不按「字体对象」记

### 之前

```csharp
private Font _metricsFont;
private readonly Dictionary<char, int> _advances;

private void EnsureMetrics(Font font)
{
    if (_metricsFont == font) return;   // 按对象引用比较
    _metricsFont = font;
    _advances.Clear();                  // 换一个 Font 实例就整表清空
}
```

而字号搜索是这样的：

```csharp
for (float size = start; size > SmallestFontSize && !found; size -= 1.0f)
    using (Font candidate = QuoteFont(size))     // 每档新建一个 Font
        if (_quoteView.FitsBlock(candidate)) ...
```

**每个候选字号都是一个新对象**，于是每试一档就把整张宽度表清空，所有字符重新用 GDI 量一遍。

那张表的注释写的是「fit search 会问五十个不同宽度，每次重量会让拖动爬行」——它防的是**同字号、不同宽度**（拖动下限的探针确实是这样），防不了**不同字号**。**表是为这个循环写的，却被这个循环废掉了。**

### 现在

按字号分桶：

```csharp
private sealed class GlyphMetrics { Dictionary<char,int> Advances; int LineHeight; }
private readonly Dictionary<float, GlyphMetrics> _metricsBySize;
private string _metricsFamily;
private FontStyle _metricsStyle;
```

- 键是 `Math.Round(font.SizeInPoints, 2)`——整档步进和小数起点落在同一个桶里
- **字体族或字形变了才整表清空**，因为那时每个字形都变了
- 容量上限 128 档，超了整表丢掉重来（正常拖动到不了）

行高也进同一个桶，所以 `NaturalLineHeight` 和字宽不会各量各的。

## 验证

两处缓存都不能靠「看代码觉得对」——缓存的两种失效方式是**永远不命中**（性能白费）和**过期了还在用**（画面错）。两种都做成可观测的：

- `QuoteGlyphMeasures`：累计用 GDI 量过多少个字符。连续两次 `RefitQuoteFont()` 后，这个数**不许再涨**（自检 249）；换一个搜索没试过的尺寸后，**必须涨**（自检 250）——后半条是为了防止计数器本身卡死，让前半条变成同义反复。
- `QuoteBackgroundCacheBuilds`：缓存构建次数。同尺寸重复取用**不重建**（255）；改尺寸（257）、改显示方式（260）**必须重建**；清掉图片后缓存**必须释放**（261/262）。

| 项 | 结果 |
|---|---|
| 卡片尺寸 | 14 组，注入 68/68 |
| 字号与内容库 | 13 组（新增 F20），注入 **117/117** |
| 便携/对齐/改名 | 4 组，注入 37/37 |
| .NET 8 纯逻辑 | 160 项 |
| 图标 / PE | 18+4 / 全过 |
| 自检断言 | **252 条**，最大 262，无重复无缺号 |

`sh verify_all.sh` 11 步 0 条失败。F20 的 10 条注入全部报出，包括「背景图又回到每次重绘都缩放」「缓存不看尺寸」「字号表按 Font 对象做键」——**这三条正是这次修的东西，它们能报出来才说明断言盯的是真地方**。

---

## 一点说明：为什么先做这两项

它们**不改任何行为**，所以风险只在「缓存键漏了一个分量」和「缓存没释放」，而这两点都能用计数器直接验。相比之下，导出为图片、吸附对齐那些是加功能，要重新设计交互。

另外，这一轮也说明一件事：**性能问题不总是「算法太慢」**。这两处都是「缓存写好了，但键选错了」——一个按对象引用、一个压根没有。**加缓存时先问：它的键是不是真的覆盖了输出依赖的全部输入。**
