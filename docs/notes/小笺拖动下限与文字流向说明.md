# 拖动下限与文字流向：为什么「横排最小高度 / 竖排最小宽度」调不下去

版本 0.9.0。修的是这两条抱怨：

> 文字横排时卡片最小高度调整……还是不行
> 文字竖排时卡片最小宽度调整……还是不行

两条抱怨是**同一个错误**，而且是上一版（0.8.0，最小宽度那次改动）**新引入**的。0.7.0 修掉固定最小高度、0.8.0 修掉固定最小宽度，两次都把「下限」换成了「面积最小的那张卡片」；那个数字对，但它被当成了**一个点**用，而能装下文字的尺寸其实是一整条**曲线**。

---

## 一、根因：把曲线剪成了两截

一段文字能放进去的卡片尺寸不是唯一解。

横排文字从左到右流，宽度决定折成几行，行数决定高度。于是：

- 卡片**宽** → 文字折成一行 → 卡片可以很**矮**；
- 卡片**窄** → 文字折成很多行 → 卡片必须很**高**。

每一个宽度配一个高度，这些配对连起来是一条曲线。两端的面积差不多：宽而一行高，和窄而多行高，占的背景几乎一样多。

上一版的做法是：在这条曲线上找**面积最小**的那个点，然后把它当成拖动下限的**两个轴一起夹住**。问题就在这里——那个点落在曲线中间，于是：

| 卡片形状 | 需要的尺寸 | 面积最小的点 | 结果 |
|---|---|---|---|
| 宽而一行高 | 宽度大、高度 40 | 107 × 81 | **高度到不了 40**：被 81 挡住了 |
| 窄而多行高 | 宽度 38、高度几百 | 107 × 81 | **宽度到不了 38**：被 107 挡住了 |

两端全部够不到。表现就是用户看到的：卡片一拖宽，高度再也压不下去；卡片一拖高，宽度再也收不进去。

`ApplyHitFrame` 按 `MinimumSize` 夹两个轴，操作系统也会按 `Form.MinimumSize` 再夹一次，所以这个「点」在两条路上都拦得住拖动。

---

## 二、修法：下限只约束「横跨文字流向」的那根轴

`CardSizeLimits` 现在有两个答案，形状不一样，用途也不一样。

### `MinimumFor` —— 一个点，给「适应文字大小（最小）」用

原来的公式没动：探针从 `SmallestView` 按几何级数走到 `WidestView`（横排探宽度、竖排探高度，另一轴留 4096 才量得到不裁字的真实足迹），取面积最小的那张卡片。

它是唯一一个**挑形状**的动作——「适应文字大小」就是要把卡片收到那个最紧凑的形状，所以它继续用这个点。

### `DragLimitFor` —— 拖动下限，一条曲线上按当前流向长度取的那一点

只约束**横跨文字流向**的那根轴：

- **横排**（文字左右流）→ 约束**高度**。宽度决定折几行，行数决定高度；宽度本身只要求放得下一个字。
- **竖排**（文字上下流）→ 约束**宽度**。高度决定分成几列，列数决定宽度；高度本身只要求放得下一个字。

而算它的时候**读另一根轴**——也就是文字流过的长度：

```csharp
public static Size DragLimitFor(Measure measure, bool vertical, int flowAxis)
{
    Size unit = SmallestTextCard;
    if (measure == null) return unit;
    int viewFlow = Math.Max(SmallestView,
        flowAxis - (vertical ? VerticalMargin : HorizontalMargin));
    Size block = vertical ? measure(WidestView, viewFlow) : measure(viewFlow, WidestView);
    if (block.Width <= 0 || block.Height <= 0) return unit;
    if (vertical)
        return new Size(Math.Max(unit.Width, block.Width + TextSlack + HorizontalMargin),
            unit.Height);
    return new Size(unit.Width,
        Math.Max(unit.Height, block.Height + TextSlack + VerticalMargin));
}
```

自由的那根轴取下限 `SmallestTextCard`——也就是「一个字一行、什么都还没写」的那张卡片：

```csharp
public static Size SmallestTextCard
{
    get
    {
        return new Size(
            Math.Max(CardState.MinCardWidth,
                SmallestGlyphWidth + TextSlack + HorizontalMargin),
            Math.Max(CardState.MinCardHeight,
                SmallestLineHeight + TextSlack + VerticalMargin));
    }
}
```

按现在的常量（左右上下各 12、`TextSlack=4`、`SmallestGlyphWidth=10`、`SmallestLineHeight=12`、退化态 32×32），它是 **38 × 40**。

### 为什么「读 flowAxis」不是老版那个坑

上一版下限跟着卡片当前尺寸走，卡片就顺着一条不断下移的下限一直缩。这次读的也是当前尺寸，但读的是**另一根轴**：

- 横排拖**高** → 宽度没变 → 高度下限没变。拖短一点，下限不会跟着降。
- 横排拖**宽** → 高度下限会降（文字折行少了），但高度下限从不看高度，所以**两根轴之间没有环**。

两轴之间没有环，是这套设计成立的全部理由。有环就会自激：下限动 → 卡片动 → 下限再动。

## 三、各调用点怎么分的

| 位置 | 用哪个 | 为什么 |
|---|---|---|
| `UpdateCardSizeLimits` | `DragLimit()` | 每次 `OnResize` 重算。宽度变了，文字折行结果就变了，高度下限跟着变——这正是「拖宽之后能压矮」的机制 |
| `FitCardToText`（「适应文字大小（最小）」） | `SmallestCard()` | 唯一挑形状的动作，收到面积最小的点 |
| `GrowCardToText`（字号调大后撑大卡片） | `DragLimit()`，撞到桌面上限时退回 `SmallestCard()` | 只沿「文字必须有」的那根轴长大，另一根轴留在用户放的地方；那一根轴撑不下时，另一根轴是唯一出路 |

参照字号仍然走 `WithFloorMeasure`：自动适应开着时按 `QuoteView.SmallestFontSize` 量（常数，不跟着卡片走），关掉时按用户自己选的字号量（绝对值，也不跟着卡片缩）。

## 四、这次改动顺手修掉的一个 bug

「适应文字大小（最小）」以前和拖动下限共用同一个点，所以 `Size = 点` 永远不会被 `MinimumSize` 夹住。现在两者分开了：一张拖窄了的横排卡片，高度下限比面积最小的那张卡片**高得多**，而 `Form.Size` 的 setter 会夹到 `MinimumSize` 上——不清空下限就设尺寸，这一步会**静悄悄地什么都不做**。

所以 `FitCardToText` 进门第一件事是把下限清回退化态：

```csharp
MinimumSize = new Size(CardState.MinCardWidth, CardState.MinCardHeight);
for (int pass = 0; pass < 4; pass++)
{
    Size wanted = SmallestCard();
    if (wanted.Width == Width && wanted.Height == Height) break;
    Size = wanted;
}
UpdateCardSizeLimits();   // 按新宽度把下限算回来
```

`UpdateCardSizeLimits` 的「已经比下限小 → 让位」那条守卫没动：自动字号关掉时，卡片可能本来就比下限小（字号刚被调大），撑大它又会让字号跟着宽度再变，转回来又动下限。

## 五、一个诚实可见的副作用

**拖窄横排卡片时，卡片会变高。**

以前宽度下限是 107（面积最小那个点的宽度），拖不过去，所以看不见这件事。现在宽度可以自由收窄到 38，而文字折行多了就必须有地方放——这是文字真的需要更多地方，不是回弹。

要钉住的是它**有底**：宽度下限是常数 38，所以这种抬高必然停在某个有限值上，卡片不会缩成一条竖线。模拟器里单独归了一组断言（I 组）查这件事。

## 六、验证

### 模拟器（`verify_shrink_sim.py`）

带状态的模拟器，度量模型写明在脚本头（1pt = 1.333px、行高 1.5 倍），其余每一步都照源码的算术走。结论不依赖那两个系数的具体取值，依赖的是「字宽随字号单调增」和「视图越窄折行越多块越高」——这两条真机同样成立。

横排 40 字，最小高度随宽度的变化：

| 宽度 | 40 | 120 | 260 | 460 | 900 | 1600 |
|---|---|---|---|---|---|---|
| 最小高度 | 448 | 80 | 49 | **40** | **40** | **40** |
| （一字卡片的下限是 40） | | | | | | |

竖排 40 字，最小宽度随高度的变化：

| 高度 | 40 | 120 | 260 | 600 | 1200 |
|---|---|---|---|---|---|
| 最小宽度 | 400 | 74 | 46 | **38** | **38** |
| （一字卡片的下限是 38） | | | | | |

旧公式（拿点当下限）在同一条曲线上：横排 40 字，宽度从 40 一直拖到 1600，最小高度**始终是 254**——正是用户抱怨的现象。

断言分组（全部对新代码通过）：

| 组 | 断言 |
|---|---|
| A1 | 「适应文字大小（最小）」那个点与卡片当前尺寸无关 |
| A2 | 拖动下限**只读流向轴**，固定流向长度扫另一根轴，下限必须一模一样 |
| B | 下限处文字装得下，宽度和高度都要 |
| C | 面积最小那个点不是窄条也不是扁条（离 1px 细网格最优不超过 1.25 倍） |
| D | 只拖被约束的那根轴，卡片沿该轴只许变小或停住 |
| E | 停住时 `MinimumSize` 正好等于下限 |
| F | 一行小字的下限高度低于旧的固定 56 |
| G | 同一段文字的下限比上一版窄，且面积没有变大 |
| H | 拖宽 / 拖高时下限**单调不升**，而且**降得到一行 / 一列** |
| I | 对角拖窄会因折行变高，但有底、必须停下、停下时文字完整 |
| J | 「适应文字大小（最小）」从极端形状出发也缩得到那个点 |

`--old` 用被换掉的公式跑同一套断言：H/J/F/G 共 9 条报出。

### 源码级断言（`verify_size.py`，14 组）

新增 Z16 组，钉住：

- `DragLimitFor` 横排分支把宽度钉在 `SmallestTextCard` 上、把高度算在块高上；竖排镜像
- 量块时按流向轴取视图，另一轴留空
- `viewFlow` 减的是「横跨」那根轴的边距（竖排减 `VerticalMargin`）
- `SmallestTextCard` 两个轴都用「一个字 + 内缩 + 边距」算，并兜在 `CardState` 退化态下限上
- 三处取值各就各位：`UpdateCardSizeLimits` 用 `DragLimit()`、`FitCardToText` 用 `SmallestCard()`、`GrowCardToText` 用 `DragLimit()` 并在撞顶时退回 `SmallestCard()`
- `FitCardToText` 先把 `MinimumSize` 清回退化态

62 处反向注入全部报出；对 v0.8.0 那份源码跑，报出 15 条；对本版 0 条。

### 自检（`XiaoJian.exe --self-test`，Windows）

新增断言 132–143：

- **132–134**：横排卡片拖宽 → 高度下限必须降，而且卡片必须真的能拖到那个更低的下限上、文字仍然完整
- **135–137**：竖排卡片拖高 → 宽度下限必须降，镜像同左
- **138–140**：纯算术钉 `DragLimitFor` 的横排分支（窄卡片 5 行 → 高度 88；宽卡片 1 行 → 高度 = 一字卡片）
- **141–143**：纯算术钉竖排分支（矮卡片 5 列 → 宽度 78；高卡片 1 列 → 宽度 = 一字卡片）
- **117/118** 改为按新的轴分工：宽度下限必须正好等于 `SmallestTextCard.Width`，高度下限必须等于 `max(一字卡片, 块高 + 内缩)`

117/118 与 132–137 那一组之前先把自动适应勾回来：字号菜单那几步把自动适应关掉了，而自动字号关掉时下限会「让位」，读出来的是上一轮的旧值。

## 七、仍然验不了的（要在 Windows 上看）

- 新下限上的**拖动手感**：模型说得清算术，说不清手感
- 小卡片上「⋯」按钮的消失与右键菜单
- `MyQuoteCard.lnk` 改写、任务栏 / 托盘 / 属性页图标渲染
- **DPI**：文字字号是 `GraphicsUnit.Point`，会随 DPI 缩放，而下限里的像素常量（38、40、边距 12）不会。`app.manifest` 声明了 `PerMonitorV2`，`XiaoJian.exe.config` 里没有 `ApplicationConfigurationSection` 覆盖，`AutoScaleMode` 实际是 `None`。所以在 125% / 150% 缩放的显示器上，可拖到的最小尺寸会**略大于**文字本身。这是已知限制，已在 CHANGELOG 里写明
