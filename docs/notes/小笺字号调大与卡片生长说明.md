# 字号调大与卡片怎么长：为什么「文字增大到一定大小后无法再变大」

版本 0.9.1。

用户抱怨：

> 文字增大到一定大小后无法再变大

这一条不在「卡片最小尺寸」那条线上，而在「字号菜单」那条线上：`文字设置 → 大一点 / 小一点 / 设为最小 / 恢复默认字号`。复现之后发现根因有两个，而且**第二个是上一个版本（0.9.0）改出来的**。

---

## 一、复现

照 `Forms.cs` 现在的实现建模，在 1920×1080 桌面上拿一张 200×200 的横排卡片、26 个字，反复点「大一点」：

| 点击次数 | 字号 | 卡片 | 文字完整 |
|---|---|---|---|
| 第 20 次 | 47 | 200×944 | 是 |
| 第 25 次 | 57 | **200×1080** | **否** |
| 第 30 次 | 67 | 200×1080 | 否 |
| 第 45 次 | 96 | 200×1080 | 否 |
| 第 46 次 | 96 | 200×1080 | 字号没变 |

两个现象叠在一起：卡片在第 25 次就顶到屏幕高度再也不动，字号却一路加到 96，每加一点都只是多裁掉一点文字。

## 二、根因一：长错了目标

`GrowCardToText` 的循环是这样：

```
wanted = DragLimit()                       // 只约束「横跨流向」那根轴
if (wanted 任一轴 > MaximumSize)           // 那一根轴顶到桌面了
    wanted = SmallestCard();               // ← 退回「面积最小」那张卡
next = (clamp(Max, max(W, wanted.W)), clamp(Max, max(H, wanted.Height)))
```

`DragLimit()` 对横排卡片返回的宽度是常数 38（「一个字」那张卡），所以**它只会把卡片往上长**。高度顶到桌面之后，唯一的出路是让卡片**变宽**——宽了，文字折行就少了。

而 `SmallestCard()` 算的是**面积最小**的那张卡。问题就在这儿：**大字号下，面积最小的那张卡是「一个字一行」的窄条。**

拿 26 个字、96 磅来算（每字约 128px 宽、每行约 144px 高）：

| 形状 | 卡片 | 面积 |
|---|---|---|
| 一个字一行 | 38 × 3772 | 143 336 |
| 挤成一行 | 4120 × 172 | 708 640 |

面积最小选了那个 38 宽、3772 高的窄条。它比卡片**现在的宽度还窄**，于是 `Math.Max(Width, 38) = Width`，什么都没长，循环立刻退出。

卡片就此停住。字号还在往上加，加多少裁多少——从外面看就是「文字长到某个字号再也长不大了」。

## 三、根因二：字号会长到裁字

源码里 `SetManualFontSize` 上面写着：

> the card is then grown to hold the text so the new size is never handed back to the user as clipped text

也就是「卡片长到装得下，文字不许被裁」。这句话只做到了一半：卡片确实会长，但**长到头之后字号并没有停下来**，而是继续把文字裁下去。小屏 + 长文字时这一半就会露出来——1024×600 的桌面上放 50 个字，字号加到 96，卡片 1024×598，文字被裁。

## 四、修法

### 新增 `FlowFitFor`：`DragLimitFor` 的逆运算

`DragLimitFor` 问的是「**给定**流向轴有多长，横跨那根轴至少要多大」。`FlowFitFor` 反过来问「**给定**横跨那根轴还有多少地方，流向轴至少要有多长」：

```csharp
public static Size FlowFitFor(Measure measure, bool vertical, int across)
```

- **横排**：`across` 是可用的**高度**。沿宽度从小到大找第一个「块高 + 内缩 ≤ across」的候选。
- **竖排**：`across` 是可用的**宽度**。沿高度从小到大找第一个「块宽 + 内缩 ≤ across」的候选。

折出来的行/列只会越来越少，所以**第一个装得下的候选也就是最小的那个**——探针方向不能反，反了就成了「越长越好」。

全都装不下时（文字比任何卡片都长）返回**最长**的那一个：那是留在卡片外的文字最少的一个。

拿 harness 里那份假文字（20 字、每字 8px、每行 16px）钉出来的数：

| `across` | 结果 | 折成几行 |
|---|---|---|
| 108（折 5 行就够） | 62 × 108 | 5 |
| 60（只折 2 行才够） | 118 × 60 | 2 |

可用高度越紧，卡片越宽。竖排是镜像（可用宽度越紧，卡片越高、更窄）。

### `GrowCardToText` 改用它

```csharp
if (wanted.Height > MaximumSize.Height || wanted.Width > MaximumSize.Width)
{
    bool vertical = _card.VerticalText;
    int across = vertical ? MaximumSize.Width : MaximumSize.Height;
    wanted = WithFloorMeasure(delegate(CardSizeLimits.Measure measure)
    {
        return CardSizeLimits.FlowFitFor(measure, vertical, across);
    });
}
```

### `SetManualFontSize` 补上早就该有的那一步

```csharp
FitQuoteFont();
GrowCardToText();
BackOffToFittingSize();      // ← 新增
```

`BackOffToFittingSize`：卡片已经长到桌面那么大、文字还是装不下时，把字号**往下走**到装得下的最大一档。卡片铺满整个桌面就是路的尽头，「大一点」应该停在那里，而不是悄悄把文字裁掉。

### 修好之后

同一个场景（1920×1080、26 字、200×200 起）：

| 点击次数 | 字号 | 卡片 | 文字完整 |
|---|---|---|---|
| 第 25 次 | 57 | 273×1061 | 是 |
| 第 30 次 | 67 | 305×1061 | 是 |
| 第 40 次 | 87 | 534×1067 | 是 |
| 第 45 次 | 96 | 598×1067 | 是 |

卡片开始往宽里长，文字一直完整，字号长到 96（设计上限）才停。

## 五、验证

### 带状态模拟器（`verify_font_sim.py`，第 5 组）

把「反复点『大一点』」这条链路整个建出来，跑 **4 种文字 × 2 种桌面（1920×1080 / 1366×768）× 60 次点击**：

- **任何一档字号下文字都不被裁** —— 这一条在改动前会被抓出 4 处（26 字 / 50 字，两种桌面各一处）
- **字号没长到上限、宽度也还有余量就停住** —— 说明还有地方可以长

`--regress-flow` 把 `GrowCardToText` 退回「面积最小」那个目标、并且不做字号退回，用来确认断言真的抓得住：报出 4 处「文字被裁」。

有一条「合理停住」的情况要区分清楚：1366×768 桌面上放 50 个字，字号停在 92.1、卡片 1366×763。这不是缺陷——**宽度已经到顶**（1366 = 桌面宽度），文字也完整。所以「字号停住」要同时满足「没到 96」和「宽度还有余量」才算问题。

### 源码级断言

`verify_size.py` 新增 **Z17 组**（`FlowFitFor` 本身：探针方向、按流向轴取视图、两个分支各自的判据、末尾那条兜底），Z16 组补两条（`GrowCardToText` 撞顶时用 `FlowFitFor`；`SetManualFontSize` 里有 `BackOffToFittingSize`）。`verify_font_library.py` 的 F4 组同步改认新写法，并补一条查 `SetManualFontSize`——`BackOffToFittingSize` 在 `SetManualFontSize` 里而不在 `GrowCardToText` 里，只看后者的方法体是抓不到它的（踩过一次）。

反向注入 **66 处全部报出**（尺寸）、**27 处全部报出**（字号与内容库）。

## 六、仍然验不了的（要在 Windows 上看）

- 字号退回那一档的**手感**：点一次「大一点」没反应时，用户能不能看出「卡片已经铺满桌面了」
- 卡片长到接近全屏时的拖拽与置顶行为
- 任务栏 / 托盘 / 属性页图标渲染
- **DPI**：字号用 `GraphicsUnit.Point` 会随 DPI 缩放，`FlowFitFor` 里的像素常量不会。125%/150% 缩放下「铺满桌面」那个终点会来得比 100% 时早一些
